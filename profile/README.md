## Q4CO 是什么

Q4CO 是面向**量子计算与组合优化**的开放协作项目。我们希望把问题数据集、求解算法、模拟与真实硬件执行、评测协议和开销分析连接起来，建立可以被检查、复现和持续改进的公共研究基础设施。

我们关注的不只是“量子方法能否求解这个问题”，更是三个具体问题：

- **差距在哪里？** 在相同任务和明确预算下，量子方法与强经典基线在解质量、达标时间和总开销上相差多少？
- **价值来自哪里？** 收益来自量子执行、跳跃算子、问题结构，还是经典预处理、调参或后处理？
- **需要什么硬件？** 要缩小这些差距，真正需要提升的是规模、连通性、精度、保真度、可执行深度，还是反馈与采样吞吐？

**不预设量子优势；让优势、局限和负结果都成为可复现的证据。**

## JumpBench：跳跃能力评测

**跳得更远，不等于跳得更好。** Q4CO 希望衡量的是：从同一个局部极小值出发，一种跳跃方案能否在给定预算内，帮助求解过程进入更好的解区域。

![JumpBench 概念图：从局部极小值提出候选解，经固定局部搜索进入更优解区域；曲线仅为概念示意](https://raw.githubusercontent.com/Q4CO/.github/main/profile/assets/q4co-jumpbench.svg)

规划中的评测分为三个环节：

1. **建立起点池。** 明确局部最优所对应的邻域，例如单比特翻转；筛选并验证局部极小值，在可认证的实例上按距全局最优解集合的最小汉明距离分层，例如 10、20、30。
2. **比较跳跃方案。** 在相同问题与起点上，比较量子线路、数字—模拟混合方案、经典扰动 / 重启和 AI 引导提议；量子方案可分别通过 MPS 等模拟后端与真实硬件执行。
3. **统一评价落点。** 对候选解使用相同的可行性修复与局部搜索，再比较跳跃后的最终解。原始候选解的质量、可行率和全部后处理开销也独立保留。

核心指标包括：**改进成功率、目标值改进量、达到目标质量的时间 / 开销，以及多轮跳跃后的累计收益**。汉明距离变化、跳出当前吸引域的频率等作为辅助诊断，不单独等同于优化收益。

公平比较需要同一起点池、公开调参规则和明确预算；除共享后处理的算子对照外，还应提供等总预算的强经典端到端基线与消融实验。

> **距离标签的边界**：只有能够验证最优性和相应距离时，才使用“距全局最优解集合”的标签。若只能得到一个指定最优解或最佳已知解，则记录“距该参考解的距离”，不冒充到整个最优解集合的最小距离。筛选后的起点池也不代表所有实际问题的分布。

## Hardware-native：保留真实硬件证据

我们单独设置 hardware-native 方向，研究与设备原生拓扑和相互作用相匹配的问题，尽量减少非原生分解、嵌入和路由对算法表现的干扰。

**Native 不是“运行没有开销”。** 是否免嵌入、免路由或免特定编译步骤，必须对具体实例与设备逐项说明；控制程序生成、校准、状态制备、读出、通信和经典后处理仍需记录。

规划中的实机记录应包含：

- 问题版本、编码、完整算法配置、随机种子与软件版本。
- 设备型号、可用拓扑、执行日期、可公开的校准信息，以及线路 / 脉冲 / 演化程序。
- Shots、原始样本或计数、失败与丢弃记录、误差处理和后处理规则。
- 设备执行时间与端到端时间；排队时间单列，说明计时边界。

**经典基线求解同一目标与约束，不被人为限制为量子设备的连接拓扑。** 在已约定预算与许可条件内，允许其使用适合该问题的高效实现。

## 六维评测与硬件需求

![六维评测框架：解质量、达标时间、跳跃收益、可扩展性、稳健性、资源效率；示意图不包含实测分数](https://raw.githubusercontent.com/Q4CO/.github/main/profile/assets/q4co-evaluation.svg)

| 维度 | 要回答的问题 |
| --- | --- |
| **解质量** | 最终解是否可行？与已认证最优值、有效界或明确标注的参考值相差多少？ |
| **达标时间** | 达到预先声明的质量与成功概率需要多久？未达标的试验如何计入？ |
| **跳跃收益** | 相对固定局部搜索与等预算经典对照，跳跃是否带来稳定的额外改进？ |
| **可扩展性** | 当规模、阶数、密度与约束复杂度提高时，质量和成本如何变化？ |
| **稳健性** | 跨实例、起点、种子、噪声与校准周期，收益能否保持？ |
| **资源效率** | 在指定质量目标下，消耗多少量子调用、经典算力、内存及可核验的费用？ |

六角图是结果摘要，不是脱离任务的“总战力分”。所有打分应公开原始指标、归一化规则、测试集合、预算和不确定性；没有测量的数据标为缺失，不填零，不制造综合排名。

**硬件需求另建画像，不与算法成绩混为一谈：**

- **规模与结构：** 可用量子比特数、连接拓扑、支持的相互作用阶数、嵌入与辅助变量需求。
- **精度与可执行性：** 系数 / 控制精度、相关误差、可执行线路深度或演化时间。
- **系统能力：** 采样吞吐、读出与复位、通信、经典反馈延迟及稳定运行能力。

开销评估器将“已测量开销”与“基于假设的资源估计”分开报告。由实验外推的硬件需求必须附带适用问题、误差模型和假设，不把预测写成实测结论。

## Gap：把差距定位到具体环节

我们希望每一份报告都能区分三类差距：

- **算法差距**：在同一原始问题上，量子方法与强经典方法的解质量—预算曲线有何不同？理想模拟可以帮助分析算法，但模拟耗时不等同于量子设备耗时。
- **执行差距**：在受控的算法配置和采样条件下，理想模拟、噪声模拟与真实硬件之间损失了多少性能？映射、有限精度、噪声和采样分别如何影响结果？
- **系统差距**：把编译、调参、通信、采样和后处理全部纳入后，内核层面的收益还剩多少？

归因依赖配对实验与消融，不把这些影响预设为可直接相加。硬件需求应从可验证的差距出发，而不是只从量子比特数量出发。

## 如何让比较可信

- **强经典基线随问题与时间更新。** 为合适的问题配置精确求解器、退火 / 平行温度、禁忌搜索、大邻域搜索等对照，记录实现、版本、调参与运行平台；不假设存在适用于所有问题的单一 SOTA。
- **同时报告内核与端到端表现。** 建模、编译、嵌入、调参、量子执行和后处理的成本清楚分账；AI 方法说明训练、预训练来源与推理成本边界。
- **训练、调参与测试分离。** 固定数据版本，避免同一实例或高度相关实例泄漏到评测中；调参预算本身也属于比较条件。
- **公开完整证据。** 发布可复现配置、原始记录、失败与超时情况、聚合方法和统计不确定性。只报告最佳一次结果不构成完整评测。
- **让负结果可见。** 没有观察到收益、收益被开销抵消、模拟与真机不一致，都是值得保留的结论。

## 建设路线

以下是规划顺序，尚未完成的能力不作为现有功能承诺。

- [ ] **基础层**：建立主库与数据集库，统一问题、实例、实验配置和结果记录格式。
- [ ] **最小闭环**：提供一组可验证的小规模实例、强经典基线和可复现实验示例。
- [ ] **JumpBench**：发布局部极小值起点池、距离标签规则、统一后处理及模拟对照。
- [ ] **真实硬件**：接入门模型与数字—模拟混合等后端，发布 hardware-native 原始运行记录。
- [ ] **评测报告**：形成六维画像、完整开销报告和带假设的硬件需求分析。

### 开放协作原则

Q4CO 希望成为共同维护的公共基础设施，而不是某一家机构、某一类硬件或某一种算法的宣传平台。

- **开放使用与协作。** 在对应许可证范围内使用、修改、分发和 fork；公开讨论技术方向与评测标准。
- **尊重贡献者。** 保留贡献者的版权与署名，不以贡献为由要求独占性权利转让；维护权限是协作职责，不等同于对全部成果的所有权。
- **尊重数据来源。** 仅接收有权公开的数据，保留来源与许可；第三方数据不会因进入项目而自动改变授权。
- **以证据为准。** 维护者、赞助方和设备提供方适用同一套公开评测规则；贡献关系与潜在利益冲突应披露。
- **允许独立延续。** 鼓励复现、质疑和独立 fork；治理细则通过公开提案逐步完善。

本 `.github` 仓库采用 [Apache-2.0](https://github.com/Q4CO/.github/blob/main/LICENSE)。未来代码、文档与数据以各仓库或数据条目明确标注的许可证为准。“开放”不意味着取消版权、署名或第三方授权条件。
